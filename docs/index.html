A formal specification language for state machines

Spectre is a research-stage tool inspired by TLA+ and Quint. Describe your system as a state machine, write invariants and temporal properties, and use the built-in BFS or an external backend (TLC, Z3, Apalache) to check them.

Get started Read the book GitHub
bank-account.spec 
var balance: int
var frozen:  bool

init { balance = 0  frozen = false }

action deposit(amount: int) {
  require amount > 0
  balance' = balance + amount
}
action withdraw(amount: int) {
  require amount > 0
  require balance >= amount
  require frozen == false
  balance' = balance - amount
}
action freeze   { frozen' = true  }
action unfreeze { frozen' = false }

invariant solvency { balance >= 0 }
temporal liveness {
  always (frozen == true -> eventually frozen == false)
}
Capabilities

What Spectre includes

An overview of the current feature set. See the book for scope and caveats on each.

🔍

BFS state exploration

Exhaustive breadth-first search over reachable states. Reports the shortest action sequence leading to an invariant violation. Subject to state explosion on large models.

⚡

Bounded model checking (Z3)

Encodes the spec as SMT-LIB2 and asks Z3 whether a violation exists within a fixed number of steps. Does not prove safety for all depths.

🔄

Drift detection

spectre sync compares a Rust implementation to a spec using Z3/QF_LIA. Classifies each action as structurally unchanged, SMT-equivalent, or semantically changed — with a counterexample witness when available.

🧬

Spec mining

Extracts a spec skeleton from Rust source: struct fields become variables, methods become action stubs. Guards and invariants are not inferred — they require manual completion.

🧪

Model-based testing

Generates ITF execution traces and Rust test driver stubs. Supports five coverage modes. Requires manual wiring of the driver to the actual implementation.

🛡️

Monitor generation

Emits a monitor.rs that checks invariants at each step. Covers safety invariants only; liveness properties are not checked at runtime.

⚙️

Incremental re-verification

Prunes and re-expands only the affected portion of the BFS graph when one action changes. Requires a valid cached graph from a prior run.

🗜️

Partial-order reduction

--por skips redundant action interleavings using the ample-set heuristic. Reduces 3-node Raft from 22,432 to 6,818 states; effectiveness varies by spec.

🎯

Property-directed exploration

--property-guided steers BFS toward states near invariant boundaries. Useful for finding violations faster; not a substitute for exhaustive verification.

Verification backends

Backends

The same spec can be checked with different backends using --backend <name>. Each has different completeness guarantees and external dependencies.

Built-in

BFS (default)

Exhaustive BFS. No external dependencies. Practical up to roughly tens of thousands of states; hits state explosion on larger models.

--backend z3

Z3 BMC

Bounded model checking over a fixed step horizon. Cannot prove safety for all depths. Requires the z3 binary on PATH.

--backend tlc

TLC

Translates to TLA+ and runs TLC. Required for liveness and fairness properties. Requires Java and the TLC jar (~80 MB).

--backend apalache

Apalache

Symbolic model checker backed by Z3. Requires Java and the Apalache distribution. Support is less tested than TLC.

Getting started

Install Spectre

Pre-built binaries are available for macOS, Linux, and Windows. Go ≥ 1.24 is required to build from source.

1

Download the binary

Get the latest release for your chip from the Releases page.

# Apple Silicon (M1/M2/M3)
curl -LO https://github.com/BoundlessProducts/spectre/releases/latest/download/spectre_darwin_arm64.tar.gz
tar xf spectre_darwin_arm64.tar.gz

# Intel Mac
curl -LO https://github.com/BoundlessProducts/spectre/releases/latest/download/spectre_darwin_amd64.tar.gz
tar xf spectre_darwin_amd64.tar.gz
2

Install globally

sudo mv spectre /usr/local/bin/
spectre --help
3

Optional: install Z3 for drift detection

brew install z3
4

Verify your first spec

spectre verify examples/bank-account-violation.spec
# Finds invariant violation in one step

Current limitations

Known limitations

Spectre is a research prototype. The following are known gaps as of v0.4.0.

State explosion

The built-in BFS backend does not scale beyond roughly tens of thousands of states. Use TLC or Apalache for larger models.

Z3 BMC is not complete

Bounded model checking can find violations within a fixed step depth but cannot prove absence of violations for all depths.

Z3 set cardinality

.size() on Set<T> values is unreliable under Z3's ALL logic for integer domains. Use TLC if your spec compares set sizes.

Liveness requires TLC

The BFS backend cannot soundly check liveness (eventually, always, WF, SF) or fairness properties. Use --backend tlc for those.

Spec mining produces stubs only

The miner extracts field names and method signatures from Rust. Guards, invariants, and initial values are not inferred and must be written by hand.

Rust only

Spec mining, monitor generation, and test driver generation target Rust exclusively. Other languages are not supported.

No stability guarantees

This is a research project. The language syntax, CLI flags, and ITF format may change between releases without a migration path.

Windows less tested

Windows binaries are cross-compiled and lightly tested. Some shell-dependent features (benchmark scripts, install scripts) assume a Unix environment.

No IDE integration

An experimental LSP server is included but is not published to any extension marketplace. Editor support requires manual configuration.
